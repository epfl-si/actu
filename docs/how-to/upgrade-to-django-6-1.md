# Upgrade to Django 6.1

**Status:** current as of 2026-09-22
**Scope branch:** `feature/django-6-x`
**Decision rationale:** see `docs/explanation/ADR-XXX Migrate the new application from Django 5.2 to Django 6.1.md`

## TL;DR — what is problematic / manual

1. **Manually verify EPFL login.** The auth stack (`django-epfl-entra-id==0.0.9` + transitive `mozilla-django-oidc 5.0.2`) is officially tested only up to Django 5.2. Login is the single most critical thing to smoke-test on 6.1; it may need an upstream EPFL package update.
2. **Run the full dependency check and test suite under Django 6.1.1** — none of this has been done yet; the branch so far is ADR + one requirements line.

## Code review findings (5.2 → 6.1)

No backwards-incompatible Django 6.0/6.1 API is used by the codebase. What was checked and found clean:

- No `union()/difference()/intersection()` combined querysets, no `RawSQL`, no `order_by()`-cleared `first()/last()`, no no-argument `select_related()` (deprecated in 6.1), no no-field `values_list(flat=True)`, no `iexact` on JSON fields.
- No custom ORM expressions/fields, no custom file/email backends, no `m2m_changed` subclassing issues: the global receiver in `src/audit_log/signals.py:41` has `**kwargs`, so it safely absorbs the new `raw` argument (also now passed by `loaddata`).
- `DEFAULT_AUTO_FIELD` is set explicitly (`src/configs/settings.py:258`); Python ≥ 3.12 satisfied.
- `src/news/admin.py:10` uses explicit `list_select_related` — aligned with the 6.1 deprecation of the no-arg form.

Known deprecations to plan for (not blockers):

- `EMAIL_BACKEND`, `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_TIMEOUT` (`src/configs/settings.py:41-47`) are deprecated in 6.1. They still work but emit deprecation warnings; they will be **removed in Django 7.0**. Optional: migrate to the new `MAILERS` setting (see the 6.1 release notes, "Migrating email to mailers").
- Cosmetic: `src/configs/settings.py` still contains 5.2 doc-link URLs and the "Generated by startproject using Django 5.2.13" header.

Behavior changes to eyeball, not fix:

- Admin change forms: fields/help text/errors now render below labels; the `wide` CSS class and the `object-tools` block placement changed. Just browse the admin after upgrading.
- Signed-cookie salt derivation changed (default fallback `False` in 6.1): no impact here — sessions are DB-backed and the app is not yet in production.

## Infrastructure — validated OK

- Python: 3.14.4 — Django 6.1 supports 3.12 / 3.13 / 3.14.
- PostgreSQL: 18.3 — Django 6.1 requires PostgreSQL 15+ (dropped 14).

## Manual checklist to complete the upgrade

1. Run `python -Wd manage.py test` (full suite) — `-Wd` surfaces the 6.1 deprecation warnings (email settings, etc.).
2. **Smoke-test EPFL login** (`django-epfl-entra-id` + OIDC flow): authenticate, logout, restricted-rights redirect to `/forbidden`. This is the highest-risk step.
3. Browse the Django admin (layout changes) and exercise a typical edit page.
4. Check the DRF API endpoints and regenerate/serve the OpenAPI schema (`drf-spectacular`).
5. Once green, continue development on 6.1; evaluate Django 6.2 LTS (April 2027) separately per the ADR.
